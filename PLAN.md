# Project "Leyline" — High-Level Plan

*A digital deckbuilding + tactical hex-combat game. Working title: **Leyline**.*

**Status:** Initial plan · **Date:** 2026-07-23

---

## 1. Vision

A digital strategy game that fuses the **deckbuilding and variety of Magic: The Gathering** with the **positional, round-based tactics of a hex-grid tabletop wargame**. You bring a deck you built; you deploy and maneuver the units those cards summon across a hex battlefield; you win through superior deck construction *and* superior tactical play.

The two halves reinforce each other: your deck defines *what tools you have*, the board defines *how well you use them*. Neither pure luck (card draw) nor pure calculation (chess) should dominate — the target is **~70% skill, ~30% variance**, where variance creates fresh situations rather than deciding games.

### Design pillars
1. **Every card is also a board decision.** A card is never just "resolve and forget" — playing it means *where*, *when*, and *facing what*.
2. **Position is a resource.** High ground, chokepoints, flanking, and zone control matter as much as card advantage.
3. **Readable depth.** Simple to parse a board state at a glance; deep in the interactions. Complexity lives in card combinations, not in fiddly rules.
4. **Deterministic at heart.** The rules engine is a pure, deterministic simulation — enabling AI, replays, networked play, and rigorous testing (see §7).
5. **Cards rewrite the rules.** The game must grow via new cards indefinitely, and cards must be able to *change the rules themselves* — not just numbers. The base rules and card effects share one representation, so "a card changes a rule" is the *only* case, never a bolted-on special case. This is the hardest architectural constraint and is designed in from day one. See `docs/rules/history/knowledge-capture-plan.md` §Part A.
6. **Asymmetric information.** Players do not share one view of the board — what each player *perceives* is a manipulable, card-driven property (Mimic, Submerged units, Mist regions). This exploits a digital-only advantage most TCGs leave on the table. Architecturally it is the same modifier/query paradigm as pillar 5, applied to a *perception* axis: one authoritative true state, projected into per-observer views. See `docs/rules/asymmetric-information.md`.
7. **Champions.** *(Secondary pillar.)* Each player is embodied by a single **Champion** — the only entity that can draw mana from the land and *channel* it into magic. It is the resource-network **root** (D8), the **win condition** (kill the enemy Champion to win — no separate Base, D9), and an exposed board piece, all at once. It runs the **same two-resource shape as a creature** (D9, revised 2026-08-06): *mana* (many spells/units per turn) and its own **Action Points** spent on draw / bond / move / fight / activate an ability — mechanically a special king-like creature, not a third economy. That resource-allocation puzzle is the game's second core decision layer. The in-match Champion is a special card type inside the deterministic core; all persistent progression lives in a **separate meta-layer** that hands the core a resolved loadout. Progression uses **level bands** (D2): horizontal within a band, a discrete step up between bands, matched only within a band. See `docs/rules/champions.md`.

## 2. Core gameplay loop

A single **turn** for one player (D21), at a glance:

```
Beginning  ─────────────────►  Action  ──────────────────►  End
   │                              │                            │
 refresh mana/AP            play spells, spend AP to      end-of-turn
 (simultaneous);            move / attack / draw / bond   triggers
 APNAP begin triggers       / activate, any order,        (APNAP)
                            until you finish (opponent
                            may respond after EVERY
                            action — priority/stack)
```

Players alternate turns. A match is: **build deck → deploy from your realm → maneuver → fight → kill the enemy Champion.**

## 3. Key systems

### 3.1 The board (hex grid)
- **The board comes from a *map card* (D11)** — a fourth match component (with card deck, terrain deck, Champion). Maps are a strategic choice, come in **sizes**, and **map size sets the terrain-deck size**. A map defines: Layout (which cells exist; "holes" = **void/aether** terrain), both start positions, each player's **home ground** and **neutral ground** (each populated by a map-level rule, default random/fixed respectively), each hex's **Terrain Type** (a worldbuilding classification, decoupled from a card's Element, D52), and optional **landmarks**. The engine consumes one resolved map as **data** (cells keyed by cube/axial coord). See `docs/rules/map.md`.
- **Hex grid** for 6-directional movement and cleaner adjacency/flanking than squares. The engine exposes adjacency, distance, path, and **line-of-sight** as queries (LOS serves Ranged *and* Mist).
- **Three vertical levels per hex (D12, D41):** Surface / Air (flying) / Underground (submerged), each capacity 3; the **Underground level is hidden by default** (pillar 6).
- **Terrain** is a **cell property** (affects move cost, LOS, and mana via the D8 network — the mana graph is a subgraph of the board graph).
- Each player's **Champion starts on a map-defined home tile**; no separate destructible base — the Champion is the objective (§3.5, D9).

### 3.2 Cards & deckbuilding (the MTG half)
- **Card type is a data-driven tag (pillar 5), not a fixed class (D17, updated D39).** Every card type shares one generic play-a-card procedure, so no umbrella term is needed anymore. Seed types:
  - **Creature** (Unit) — mobile permanent; **three stats: Attack / Life / AP** (D10). AP is its private per-turn action budget; **mana is a single shared pool** (see `docs/rules/economy.md`).
  - **Companion** (D22) — a Champion's signature "friend," deckbuilding-gated to specific Champion(s); Creature-shaped (Attack/Life/AP) but can also **bond terrain** like a channeler — the mana it draws stays in a **private pool** it alone spends, on its own printed abilities. See `docs/rules/companions.md`.
  - **Structure** — stationary, **non-carryable** permanent; subtypes (e.g. *Building*) fit the hex/location theme. Absorbs non-equippable "artifacts."
  - **Item** — **carryable** permanent (pick up / equip).
  - **Spell** (D39) — the one-shot type; resolves to an Aether **trace**, leaves no permanent.
  - *Pre-game / separate economy, outside the card-type list:* **Map** (§3.1), **Champion** (pillar 7), **Terrain** (§3.3).
- **A legal match brings four components (D11):** card deck, **terrain deck** (§3.3), **Champion** (§pillar 7), and a **map** (§3.1) — all legality-constrained; map/terrain-deck sizes are linked.
- **Deckbuilding rules:** deck size, copy limits, and a **faction/color identity** system to give decks flavor and force meaningful choices. (Theme deferred, but the *structure* of factions is a mechanic to design now.)
- **Data-driven:** every card is defined in data (JSON/resource files), not code — so designers can add/balance cards without engineering. This is foundational to the architecture (§7).

### 3.3 Resource system — terrain connection network (DECIDED, D8)
A **separate terrain deck** is laid out randomly in each player's home ground at start. Up to once per turn a player **connects** one more terrain reachable from their **Champion** through already-connected, unblocked terrain; connected terrain produces mana. This is a spatial, deterministic ramp that **eliminates draw-based mana/color screw** while keeping lands powerful and thought-after. 8 colors (8 unrestricted basics + restricted non-basics). The **Champion is the network root**, so advancing it endangers the economy — fusing resources to board and Champion (pillars 1, 2). A **Companion (D22) is a second, independent root** — it bonds terrain the same way, but the mana stays in a **private pool** only it can spend, never joining the shared pool. Mana **denial is positional and reversible** (occupy a node to put a connection "on hold"), never random. This is the game's signature economy and a deliberately rich core system. Full design + open questions: `docs/rules/resources-terrain.md`, `docs/rules/companions.md`.

### 3.4 Combat (DECIDED: D3, D4, D13)
- **Attacks target a terrain, a Slice and an entity; the attacked entity declares defenders** (guard mechanic, D4, D115). Every fight is an explicit `Combat` object, resolved **sequentially** now, revertible to phased (D3).
- **Damage (D13): mutual, simultaneous, attacker-assigns across gang-up defenders.** Resolution is a set of **directed damage events**, each independently modifiable — so Ranged/First Strike/Trample are keywords, not rules. **No dice, no facing/flanking/high-ground**: position matters via adjacency, Range, occupancy, and guarding, not combat modifiers.
- **Damage persists; no auto-heal** — healing is a special ability (D14, pessimistic defaults). Deterministic — variance comes from the deck, not dice.

### 3.5 Win conditions (DECIDED, D9)
- **Default: kill the enemy Champion** (Duelyst-style). There is **no separate Base** — the Champion *is* the objective, and also the economic root (D8) and most-exposed piece, so every Champion decision is loaded. You must fight *through* the map to reach it, marrying both halves.
- Secondary/alternate win conditions per faction add deckbuilding depth (control, objectives, mill-analog) — layered on as cards (the win check is an evaluated effect, not hardcoded).

## 4. The hard design tensions (resolve via playtesting)

These are the interesting problems at the MTG × tactics intersection. The plan is to prototype fast and answer them empirically:

1. **Variance vs. skill.** Where does randomness live? (Recommendation: in deck draw only; keep board/combat deterministic.)
2. **Turn structure.** Strict I-go-you-go (clean, can feel slow) vs. simultaneous/phased orders (dynamic, harder to build). *Start with alternating rounds; it's simplest to implement and reason about.*
3. **Snowballing.** Tactics games punish early losses harshly. Need catch-up valves (comeback mechanics, board resets, resource floors).
4. **Match length.** Must be satisfying yet short enough for mobile sessions. Target: **10–20 minutes.**
5. **Tempo of card play vs. movement.** How many cards/turn? How much movement/turn? This ratio *is* the game's texture.
6. **Complexity budget.** Every rule competes for the player's attention with the board. Favor fewer, deeper systems.

## 5. Game modes

Multiple modes were requested; recommended build order:

1. **Hotseat / local 1v1** — *first*, because it needs only the rules engine + UI, no AI or netcode. Fastest path to a playable game and rule validation. *Caveat: shared-screen hotseat conflicts with hidden info (pillar 6) — either add a "hide screen / pass device" step or accept degraded hidden-info fidelity in this mode only.*
2. **Solo vs AI** — the deterministic engine makes AI tractable (search over legal moves; start with heuristics, later MCTS/minimax).
3. **Online 1v1** — the deterministic engine enables lockstep or command-based netcode and server-authoritative validation. Highest infra cost; do last.

> Modes are ordered to reuse the same core. Because the engine is deterministic and headless, all three are *views* over one simulation.

## 6. Recommended technology

**Constraints:** PC-first, mobile portability later, experienced developer, serious-indie ambition with a learning goal.

### Engine: **Godot 4 (with C#)** — primary recommendation
- Free and open-source, no royalties — good for indie.
- First-class **PC and mobile** export from one codebase (satisfies the portability requirement).
- Excellent for **2D, turn-based, UI-heavy** card/tactics games (this game is not physics/3D-heavy).
- Lightweight and readable — strong for **learning game implementation** without Unity's overhead.
- C# gives you a real typed language for the rules engine; GDScript remains available for glue.

**Alternative: Unity (C#)** — choose if you want the largest asset/tutorial ecosystem and the most battle-tested mobile pipeline, and don't mind more weight and licensing considerations. Everything in this plan's architecture is engine-agnostic.

### Architecture: **deterministic rules core, separated from presentation**
This is the single most important technical decision. Full component breakdown, the client/server Host boundary, and the mode-by-mode "what runs where" matrix now live in `docs/architecture/architecture.md` (engineering decisions logged as A1–A5 in `docs/architecture/history/decisions-architecture.md`) — the shape below is the short version:

```
Rules Core (pure C#, headless, deterministic) → Perception layer (per-observer views, pillar 6)
                                                            │
                                                          HOST  (commands in / this seat's view+events out)
                                              ┌─────────────┴─────────────┐
                                     Local/Embedded                Remote/Networked
                                    (in-process, solo/hotseat)     (network → Server process, online 1v1)
                                              │                             │
                                   Human/UI seat-controller         AI seat-controller
```

Same Rules Core binary, same Host contract, either transport underneath — this is what makes "everything the server does in 1v1 must also run on the client" literally true, not just aspirational. `docs/` itself now splits the same way: `docs/rules/` = what the game is, `docs/architecture/` = how it's built (see `docs/README.md`).

Why it's worth the discipline:
- **Testable:** rules verified without rendering.
- **AI-ready:** the AI plays by generating and evaluating legal commands against the same engine.
- **Net-ready:** deterministic simulation enables server-authoritative or lockstep multiplayer with anti-cheat essentially for free.
- **Replays & balancing:** record command streams; replay and batch-simulate for balance analysis.

**Per-observer views (asymmetric information — pillar 6).** The core holds one deterministic *true state* but exposes it only through a **perception layer** that projects a separate *view* per player. The engine emits per-observer (redacted/transformed) event streams, never one global stream. Consequences: networking **must** be server-authoritative and view-redacted (clients never receive true state); the UI renders a view, never truth; AI must eventually reason from its own view, not truth. See `docs/rules/asymmetric-information.md`.

**Priority + stack (interaction).** The core includes a real priority/LIFO-stack capability so players can act on the opponent's turn (instants), enabling combat tricks and traps through one mechanism. Kept tame via defined priority windows and mostly sorcery-speed default cards. This is the largest complexity commitment in the core and touches AI (evaluate responses) and netcode (priority windows). See `docs/rules/interaction-stack.md`.

### Data-driven content
- Cards, units, terrain, and factions defined in **data files** (JSON or Godot resources), loaded by the engine.
- Enables rapid iteration and eventually a card editor — critical for a content-driven genre.

## 8. Immediate next steps

Design work runs across three parallel tracks — **Rules** (mechanics/engine-level design), **Implementation** (code), and **Content** (cards, Element identities, abilities/keywords) — split 2026-09-14 so a mechanics question and a "just write the card" question don't get tangled together. A fourth, **Track D**, holds rules questions outside the prototype scope (D104). Current-state rules live in `docs/rules/`; full decision history and reasoning (**D1–D77**) lives in `docs/rules/history/decisions.md`. **This section tracks only what's still open** — what's already decided is not repeated here; see `docs/README.md` for how the split works.

**Numbering rule (all tracks): item numbers are never reused or renumbered.** A resolved/removed item is deleted outright, leaving a gap — never causes the remaining items to shift. New items are only ever appended at the end. This is deliberate: other docs cross-reference these items by number, and a past renumbering silently broke several of those references (fixed 2026-09-22) with no way to detect it short of a manual audit.

**Track A — Rules (design review, parallel, user-led; does not block implementation):**

1. **Uniqueness / copy-limit rule (general).** Surfaced by Companions (expected to be one-ofs) but deliberately **not** a Companion-specific rule — design a general singleton/"legendary-type" mechanic (max copies in deck, max copies on the Island) that Companions, and any future card that wants the same restriction, just consume. Ties into the existing open "deck size / max copies" item in `overview.md` §6. A max-copies-on-the-Island check would be an immediate consequence of the instruction that broke it (D112), not a trigger.
2. **Simultaneous movement / a richer priority-window model.** The current strict-alternating-turns model (D21/D45) can force a bad trade purely from action sequencing: e.g. several creatures are hidden under an "area of darkness" spawned by one creature and must move along with it to remain hidden — but each move is its own action and opens a priority window, so once the spawning creature moves, the others are briefly exposed and the opponent can respond against them before they follow. The player never gets to treat "move the group" as one atomic decision. Candidate direction, not designed: the opponent doesn't gain priority until a *repeated* action on the same creature, or a spell/ability activation — letting a single creature's first move-of-the-turn (or a "move a whole group" action) resolve without opening a window. Not scoped, not evaluated against pillars 1/2/4, no prototype cards yet. See `docs/rules/interaction-stack.md`, `docs/rules/overview.md` §3. **Extends to attacks (D117):** acting simultaneously is also where the combat phase's depth could come back — several attackers on one hex and "who defends whom" (`history/playtest-variants.md` §Combat procedure).

11. **Continuous effects and the Mind, in both directions.** **Into the Mind:** does — and how does — a continuous effect (modifier) apply to a Card sitting in Hand or Library, before it's ever a Permanent (e.g. a hypothetical "target creature card in your hand gains +1/+1/+1")? **Out of the Mind:** abilities that function while their card is in Hand, Library or Discard ("as long as this is in your hand, creatures you control have haste"; cycling- or channel-style activated abilities). The prototype scope (D104, D108) lets a card's abilities function only on the Island. `object-properties.md` only describes how such a modifier would *propagate* if one existed, not whether/how one attaches to a Card in the first place. Distinct from the property inventory (`object-properties.md` §5) — this is whether the modifier system reaches into Hand/Library at all. See `object-properties.md` Open Question 1.
31. **Choices assigned to Neutral.** A choice bound to a target-relative chooser ("T1's controller chooses one: …") lands on Neutral whenever T1 is Neutral — and Neutral never makes choices (Neutral A/B are turn-order seats only). Same gap for any resolution-time choice ("a creature of their choice," "each player chooses") that can reach a Neutral controller. Candidates, none evaluated: a fixed default (e.g. first listed option), the permanent's Behavior ranks the options, or the choice/instruction does nothing. Note that some options already no-op for Neutral on their own (Neutral has no hand to discard from). See `docs/rules/neutral-permanents.md`, `docs/rules/interaction-stack.md` §Binding.
32. **Drop D83's "relation" category: every target qualifier becomes a selection constraint.** Today (D83, `interaction-stack.md` §Binding) a target qualifier is consumed at binding *unless it names a different target*; such a clause is a **relation**, stays in the trace text, and is rechecked at resolution — e.g. "create a Fire Warrior on target hex within distance 1 of T1" keeps "within distance 1 of T1", so moving T1 away in response fizzles the creation. Card data must therefore mark own-qualifier vs. relation per clause. **Proposal:** every qualifier, including one naming another target, only filters that target's candidates at the Target step and is consumed at binding (T1 is already assigned when H1 is picked, so "within 1 of T1" is just a filter on H1). A recheck a designer wants is written as an ordinary instruction condition over a target-relative reference: D83's own example "deal 3 damage to target creature at target hex" becomes "deal 3 damage to target creature if it is still at its current location", which binds to "deal 3 damage to C1 if it is still at H1" ("its current location" is a reference bound at declaration, not a second target). **Gain:** the `relation` construct disappears from the effect normal form; conditions already exist. **Cost:** the default flips — multi-target effects are no longer dodgeable by moving unless the card opts in with an explicit condition (against pessimistic defaults). **Checked, not a cost:** Remand/Flicker still un-instantiate everything, because a trace annotates its template rather than replacing it (D70) and Remand deletes bindings with targets (D83) — consumed constraints come back with the template, and "if it is still at H1" reverts to "…at its current location". Surfaced in item 4's worked example (Cinder Verdict).
40. **Choices on permanent cards and "as this enters, choose…" abilities** (MTG's linked abilities, CR 607 — e.g. "As this enters, choose a color. This has protection from the chosen color."). Out of scope: a permanent card has no choices. **Considered direction (item 4 discussion):** make the choice at cast as an ordinary option of the Choose step, worded "Protection from a color of your choice" — no linked abilities needed; the value locks in like a mode (§4 of `object-properties.md`), so Bounce returns a card with the color fixed (the user accepts this). **Costs found:** (a) the opponent sees the choice before responding and the board can change before entry — a power level to price; (b) Flicker can't re-choose unless the card says so; (c) choosing an object ("a creature adjacent to it") can't happen at cast — it's a target under D83; (d) a permanent created without a cast (by an instruction, D88, or by the Map) has no Choose step — proposed: the creation instruction binds the choice at declaration like the creation triple (`object-properties.md` Open question 6), the source's controller choosing; a Neutral source must state the value in card text, or the card is invalid.
41. **Thresholds across repeated picks (split from the former Track A item 33, Spell properties).** `docs/rules/effect-form.md` (D95) puts outputs only on instructions, visible only inside their option instance (block scope); output = the instruction's state diff, including deaths it causes (D96). D135's one level of nesting (a resolution-time choice inside a cast-time option, with a condition) covers gating a choice and a choice reading an output. **Still open:** "Choose three, repeats allowed: deal 1 damage to target creature. If 3 or more creatures died this way, draw a card." Repeating a sentence in every option works for sums ("draw a card for each creature killed" — each pick draws for its own kills), not for a threshold no single pick reaches.

    **Considered direction, undecided:** effects carry `[output :=] [condition]`; an effect's output is the combined diff of its chosen options and is visible to later effects: `hits := you choose 3..3 repeatable { T := you choose 1..1 creature; damage(T, 1) }` · `[if died(hits) ≥ 3] you choose 1..1 { draw(you, 1) }`. Its cost: conditions in two places again (on the effect for aggregates, on the instruction for logic within one pick). Unlimited nesting (`action ::= verb arg* | effect`) was rejected by the user: a machine-readable form shouldn't need it.
42. **Ability traces become cards.** The user would like any trace to be able to become a card (Remand, "return target trace to your hand"). Permanent and Spell traces already can (D74). An Ability trace lacks three things: **(G1) name** — a name is the reference to a card definition (D99), so the permanent's name would yield a card contradicting its definition; each ability would need a definition identity of its own (e.g. "Fire Warrior: Breath"), which would also become the Ability trace's name, none in the prototype; **(G2) self-references** — "this creature" in ability text points to the source, on a card in Hand it would point to the card; **(G3) cost** — a triggered ability has none, so the card would be free (an activated ability's AP cost can be paid by the Champion). Cost, Speed, Duration and rules text (targets reset, §4) are already there.
48. **Review the effect form for expressiveness we can drop (user, 2026-10-09).** The user believes the effect form is too expressive, and with hidden information that risks ending up more complicated than MTG. Approach it mathematically: list the elements of card effects and their dependencies — amounts (`X`), modes, other choices, targets, payment choices, costs (incl. branches and optional costs), instruction outputs, conditions, cast condition, relations between targets, choosers other than you, resolution-time choices — decide which are required (target-dependent costs, `X`, illegal targets from hidden information are) and which could go to make casting simpler. Includes the user's idea of combining modes and `X` into one mechanism. Start from `effect-form.md` and the Cinder Verdict example. D135 already removed cost branches (costs now sit on options and targets) and choosers other than you at casting.
49. **What races mean mechanically (from D136's discussion).** Classes now matter through close-quarters abilities; races don't yet. Ideas from other games: **R1** home terrain — a race is stronger on its home Terrain Type (Wesnoth's movement types, StarCraft's creep); reverses D52's "Terrain Type has no mechanical effect" and competes with Element for "belongs here". **R2** race decides the body: Slice access and senses (D&D) — mostly bundles existing keywords. **R3** race decides what a fallen creature leaves (undead rise, elementals dissolve, constructs leave scrap) — touches item 39's Remnant naming. **R4** kinship bonus for standing with your own race (Teamfight Tactics' trait thresholds) — an adjacency check on every action. **R5** a Companion funds creatures of its own race more cheaply. **R6** a Neutral creature's default Behavior comes from its race (replaces D82's single default). **R7** race matters only through card text (MTG lords, tribal payoffs, weakness tags as in Fire Emblem).
50. **Deceiving a player about what they own (from item 35's discussion).** By default a player's view of their own things is true; a card may change it. User's first example: a hidden spell secretly replaces target card in an opponent's Hand with card XYZ, and XYZ gains "Mimic the target card", so it still looks the same to its owner. Problem: the owner finds out only when casting it, after paying at C1 (D135); revealing it at the cast attempt with a full refund makes the card pointless. User's preferred shape: a hidden rider the controller doesn't see, e.g. a spell that secretly adds "deal 3 damage to you" at the end; the damage is an outcome the controller sees, so the contradiction rule (D146) shows it when the rider resolves. Open: which other own-view deceptions are worth a card, and when each collapses.
52. **Truly unseen permanents (from Track A item 59, D155).** In the prototype a Pretend on a creation may only show a different permanent, so every permanent is in every belief with values. Allowing "*Pretend:* no effect" on a creation means a later trace can target (D164) a permanent the opponent has never seen, with every value `?` — nothing can then contradict those values. Revisit once the restricted rules play smoothly.
53. **Permanents in the Root at the start of the game (from Track A item 59).** Their location would be `?` to the opponent from the first moment, before any trace showed them. Out of the prototype scope.
64. **Resolution checks against choices made at resolution (from Track A item 24).** Test D85's implicit conditions against an edict, "look at the top 3 cards, put one into your hand", and "draw two, then discard a card". The prototype has no resolution-time choices (D104).
65. **A card's activated abilities other than Cast.** A card is a definition plus abilities (D142), and Cast is only one of them; MTG's Cycling is another ("pay a cost, discard this card from your Hand: draw a card"). The user wants such abilities in Leyline. Out of scope today: abilities that function from Hand, Library or Discard (`effect-form.md` §Prototype scope). To frame: which sections an ability works from, who pays it, and what trace it makes.
66. **Search (from Track B item 25).** "Search your Library for a card" picks a card among hidden ones at resolution, and choices at resolution are outside the prototype scope (D104). In scope only as a fixed search ("search your Library for a card named X"). Build it with choices at resolution (Track B item 11).

62. **Mana color in the opponent's pool belief (from Track A item 52).** In the prototype the opponent's belief of a pool is a single count, so a Pretend can claim an Element the player has no terrain for and nothing contradicts it; spotting it is left to the human. Later: a belief that includes mana color, or a conservation law such as "a claimed colored pip needs a bonded terrain of that Element" (weak — any one such terrain anywhere silences it).
71. **History beyond the current round (from Track A item 36, D163).** Any history may be read, for the whole game; the prototype reads only the current round. Build reading further back — how the track is stored over a whole game is Track B's question.
73. **Hidden changes to cost and Speed (from Track A item 72).** In the prototype a card's cost and Speed are observed in its owner's Hand, so an opponent can't secretly change them. Example card this rules out — Hidden Tariff: "Cards in target opponent's Hand cost {1} more until your next turn. *Pretend:* no effect." Allowing it needs a rule for a cast made against a view whose cost or Speed is false: candidate, extend D130's top-up from target-dependent costs to every cost (the caster may pay the difference at resolution, or the trace does nothing) and recheck Speed at resolution; the demand is a hard fact, so the bluff collapses (D131). Same question for a hidden change to the cost of an opponent's permanent's activated ability.
74. **Hidden control changes (from Track A item 72, D164).** In the prototype a permanent's controller is certain wherever its location and instance are observed, so control of a visible permanent can't change in secret. Taking a neutral permanent in an unobserved Root stays hidden only with a Pretend: an instruction names only its targets, as trace content. Relax this only for a design that plays well; the obvious example ("Gain control of target creature. *Pretend:* no effect") isn't one, since the lie breaks the first time either player uses the creature. Without a better example, controller stays observed beyond the prototype too.
75. **Pretended location in sight (from Track A item 72).** In the prototype an observed location is always true: location decides whether a permanent is observed at all (and whether a known object can be targeted), so a Pretend that wins over a sighting would make every hex untrustworthy. Illusions use a decoy instead: a real token whose content is pretended ("Create a 0/1 Decoy token. *Mimic:* it looks like target creature."). Check later whether location can be pretended in some form without that cost.
76. **Terrain Mimic (from Track A item 72).** "This terrain looks like a Plains to opponents" is outside the prototype. The terrain's owner sees the true terrain; everyone else, including a controller who bonded it without owning it, sees the Mimic (control is only decided by bonding). Candidate split: location, instance and controller certain for everyone; name, subtypes, mana production, capacity and static abilities pretendable. The open part is the readers: a move whose AP cost is checked against a false terrain is the Hidden Tariff gap (item 73) again; a credit from a mimicked terrain and an effect targeting a false subtype are ordinary contradictions.
77. **The smallest change for a location (from Track A item 72, D164).** When a copy's location belief turns out false and nothing observes the true one, it becomes `?`. Idea (user): use the smallest change instead — keep where the creature's last move, descend or similar action put it. One rule for every property is the goal; for the other properties a contradiction observes the true values, so only location is left.
78. **Cards that change what an observation shows (from Track A item 72, D164).** By default an observation shows the true values; a card may change that. Example (user): a curse "Target creature gains: its Life is observed as 1. *Pretend:* no effect" — a creature with true Life 6 surviving damage shows 1. It must be a static ability (a triggered one leaves a trace that gives it away), and a replaced value must fit what was observed (Life 0 on a creature seen standing is not applied; the true value is shown).
80. **Changing a belief by hand (from Track A item 72, D164).** Idea (user): a player who knows the meta often knows what caused a false belief, and a view that insists on something else frustrates, so a player may change any deduced value in their own copy. Moved out of the prototype to get to playtesting: it opens a side channel — set an enemy creature's Life to 0, your copy's death check removes it, it is seen standing, and the contradiction observes its true Life (the same with AP). Options: a contradiction on a value set by hand observes nothing and only restores the deduced value; or edits change only what the view shows and never feed the copy's rule steps. Belongs with item 60 (how the view presents beliefs).
81. **A Pretend that shows a different card type (from Track A item 72, D164).** A creature pretending to be a Structure ("*Pretend:* a Wall") without Mimic is outside the prototype. Open: what "Destroy target Structure" fizzling on it observes — the type, which the check read, while the rest of the false face stays?
83. **A pretended Duration (from the belief-implementation discussion, 2026-11-05).** Outside the prototype: a trace's Duration is treated as certain, so no Pretend reaches it (e.g. Mirage 3, "+1 Power. *Pretend:* +1 Power until end of turn"). **Warning before bringing it back:** a pretended Duration is always caught at the first turn-end where the true and the pretended Duration differ, in every solution and without any interaction — the trace's section is certain and the Aether is always observed, so the opponent sees the trace still in Past (or gone) against its own version. The lie only works for the rest of the current turn. Yet it needs per-copy Durations in the engine (`implementation-plan.md` G34; `Copies.FadeIn`, `FadedFor`, `DurationFor`). A card that wants this bluff can lie about its content instead ("+1 Power. *Pretend:* no effect"), which survives much longer.

**Possible simplifications** (adopt only once we're sure they don't hurt anywhere; labels are never reused):

- **S1 — Derive Physical from the ability's subtype.** An ability with a physical subtype (Move, Attack, Defend, Ascend, Descend) leaves a Physical Trace, instead of Physical being a separate flag. One axis instead of two; no card is known that wants a physical ability without a physical subtype.
- **S2 — Does terrain need a capacity?** Capacity per Slice is a terrain property (base 3, changed by static abilities, `object-properties.md`). If it never varies, the remaining room is just 3 minus the occupants, and the property could go.
- **S3 — Target-dependent surcharges only as amounts.** A surcharge another card adds ("targeting this costs …", D130) may only be mana, AP or life, so paying it never needs a choice and a top-up is a plain yes/no. **Also closes a gap accepted in D135:** a surcharge with a choice may pick an object that is a target of the same trace (target your own throwaway creature, fell it for the surcharge). Accepted until a card makes it hurt in testing.
